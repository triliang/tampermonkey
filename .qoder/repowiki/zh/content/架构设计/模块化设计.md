## 项目结构
Tampermonkey 采用“按职责分模块”的组织方式，核心入口在后台页与内容页脚本中通过注册表进行模块化加载与协作。主要模块包括：
- 核心注册表：统一的模块注册、依赖声明与动态加载
- 工具与基础能力：辅助工具、HTTP 请求、解析器、兼容层、转换器、国际化等
- 视图与交互：选项页、标签视图、HTML 工具、遮罩提示等
- 背景页业务：脚本运行调度、上下文缓存、版本迁移、更新检查等

## 核心组件
本节聚焦注册表系统与关键模块，阐明其职责、交互与扩展点。

- 注册表（Registry）
  - 提供模块注册、依赖声明、动态加载与回调机制
  - 支持原始资源缓存与按需加载
  - 提供加载完成通知与循环依赖规避
- 工具模块（helper.js）
  - 提供通用工具函数（序列化、正则、URL 处理、类型判断等）
  - 向注册表注册自身，供其他模块使用
- HTTP 请求模块（xmlhttprequest.js）
  - 封装跨域与本地资源访问，支持重试与进度回调
  - 向注册表注册运行接口
- 解析器模块（parser.js）
  - 解析用户脚本元数据与配置项
  - 生成脚本对象模型，供运行时使用
- 兼容层（compat.js）
  - 提供语法兼容转换，适配旧式脚本写法
- 编码转换（convert.js）
  - 提供 UTF-8/Base64 等编解码能力
- 国际化（i18n.js）
  - 提供消息获取与本地化切换
- 同步信息（syncinfo.js）
  - 提供脚本列表同步、时间校准与变更监听
- 视图与交互（tabview.js、htmlutil.js、curtain.js）
  - 提供选项页 UI 组件与交互提示

## 详细组件分析

### 注册表系统（Registry）
- 设计要点
  - 基于名称的模块注册与获取
  - 依赖声明与动态加载（按需拉取）
  - 加载完成回调队列与去重
  - 原始资源缓存与重复加载规避
- 关键流程
  - require：未注册则标记占位并发起加载
  - loadFile：通过 DOM 动态注入脚本或直接执行
  - register/get：注册模块对象并对外暴露
  - checkLoading/onLoad：检测所有依赖是否就绪并触发回调
- 循环依赖规避
  - 在 require 时将目标模块置空占位，避免重复加载
  - 通过占位与就绪检测实现基本的循环依赖防护

```mermaid
flowchart TD
Start(["调用 require(name)"]) --> Check{"对象已存在？"}
Check --> |是| Return["返回已注册对象"]
Check --> |否| Place["设置占位对象为 null"]
Place --> Load["loadFile(name + '.js')"]
Load --> Register["register(name, module)"]
Register --> CheckReady["checkLoading() 遍历对象表"]
CheckReady --> HasNull{"仍有占位(null)？"}
HasNull --> |是| Wait["等待其他模块注册"]
HasNull --> |否| Done["触发 onLoad 回调"]
Wait --> CheckReady
Done --> End(["结束"])
```

### 初始化顺序与上下文管理（背景页）
- 初始化阶段
  - 背景页在启动时声明所需模块依赖
  - 通过 requireCache 实现模块请求结果缓存，降低重复加载开销
  - 版本迁移与数据转换流程在初始化阶段执行
- 上下文注册（ctxRegistry）
  - 为每个标签页维护运行上下文，记录 URL、UA、统计信息等
  - 支持缓存命中与清理，减少重复计算
- 脚本运行调度
  - 根据 URL 与匹配规则确定待运行脚本集合
  - 支持缓存命中与运行统计

## 性能考量
- 模块缓存
  - requireCache：缓存最近请求的模块内容与响应头，降低重复网络开销
  - 清理周期：定期清理过期缓存，避免内存膨胀
- 加载策略
  - 动态注入脚本：通过 DOM 创建 script 标签异步加载，避免阻塞
  - 占位与就绪检测：防止重复加载与死锁
- 运行时优化
  - ctxRegistry 缓存：减少重复计算与状态查询
  - 事件与消息传递：最小化跨上下文通信成本

## 故障排查指南
- 模块未找到
  - 症状：控制台输出“未 require 或未找到”类日志
  - 排查：确认模块是否已通过 require 声明并在注册表中注册
- 循环依赖
  - 症状：模块加载卡住或报错
  - 排查：检查模块间相互 require 的链路，利用占位与就绪检测机制
- 加载失败
  - 症状：动态加载抛出异常
  - 排查：检查 loadFile 流程与网络权限；确认文件路径正确
- 国际化与本地化
  - 症状：消息未翻译或参数不匹配
  - 排查：确认 setLocale 成功加载语言包；检查消息键与占位符

## 结论
Tampermonkey 的模块化设计以注册表为核心，实现了：
- 明确的模块注册与依赖声明
- 动态加载与缓存策略
- 解耦的模块接口与扩展点
- 初步的循环依赖规避与错误恢复
在此基础上，建议进一步完善：
- 显式的模块生命周期钩子（初始化/销毁）
- 更强的循环依赖检测与报告
- 模块热替换与增量更新支持
- 统一的版本与兼容性策略文档

## 附录

### 模块开发规范与最佳实践
- 命名约定
  - 模块名使用小写与下划线，避免特殊字符
  - 模块注册名与文件名保持一致
- 依赖声明
  - 在模块开头显式 require 所需依赖
  - 避免隐式全局依赖
- 接口抽象
  - 通过注册表统一导出接口，隐藏内部实现
  - 对外仅暴露必要方法与常量
- 错误处理
  - 对外部依赖进行健壮性检查
  - 记录可追踪的日志，便于调试
- 性能优化
  - 合理使用缓存与延迟加载
  - 控制模块体积与加载数量

- 新增模块步骤
