# 检索与实时批量读取合并

## 计划

优化当前结构增强 + BM25 链路，先减少模型与工具的往返。暂不接入 Chrome DevTools MCP 或 HtmlRAG；用同一隔离页面对照普通检索读取与合并读取。保留失败后的手动定位入口，不改变目标确认、生成、运行、保存授权。

## 实施

search_dom 新增可选 readLimit（0–8）。设置 4 时，宿主先返回既有 BM25 排名中的观察引用，再通过已有 read_dom_blocks 对前 4 个不同引用独立进行实时节点验证，将结果附在 verifiedReads 中，同一次模型工具调用返回。

- 未指定或设置 0 时保留旧行为，兼容原调用。
- 组合只读取结构证据，不将词法排名判为业务目标，也不自动选择父容器。
- 成功读回、失效节点、采样截断继续分别展示；失败项不得用于报告引用。
- 内部批量读取照常计入本地与宿主工具预算，使用真实已发出引用。剩余不足 15 秒不额外自动补读。
- 系统提示优先使用 readLimit:4，已有成功读回不重复读取；修改任务仍需 inspect/review 后才能提议范围。
- 未修改网页访问权限，版本保持 0.4.3。

## 测试与对照

Harness 62 项通过。新增同一证据测试：普通检索 → 批量读取 → 合格报告需要 3 次模型调用；组合检索读取 → 合格报告需要 2 次，减少一次模型往返。两种方式均实际读取一次，工具成本没有凭空消失；组合保留截断信息和部分失效结果。

浏览器对照使用同一通用测试页面、真实 Chrome、Native Messaging、实际 Harness Worker 和确定性本地模型协议夹具。日志分别写入 evidence/2026-10-27/combined-read/baseline 与 optimized。准确调用数见 comparison.json。此对照只证明调用路径缩短及范围流程兼容，不证明真实供应商模型识别准确率提升。

## 复核

没有加入网站或广告专属规则；没有引入新的自动执行能力。原真实页面在本轮未重跑。组合读取可能读取不相关的排名候选，默认建议上限 4 控制成本；宽泛需求仍可能因截断或语义不足失败，仍提供手动定位与范围确认。下一步以真实页面复测观察总调用数、核实成功率与误选情况，不能用合成夹具的收益百分比代替真实效果。

## 最终验收与部署

同页对照两组各 24 项浏览器检查通过：只读 identify 模型调用 3 → 2，修改 modify 调用 6 → 5。比较见 [comparison.json](evidence/2026-10-27/combined-read/comparison.json)，原始链路见 [baseline](evidence/2026-10-27/combined-read/baseline/native-dom.json) 与 [optimized](evidence/2026-10-27/combined-read/optimized/native-dom.json)。读取的实际工作仍执行并计数，未宣称工具操作减少或业务准确率提高。

发布包已重建，日常后台确认空闲后温和重启，见 [部署记录](evidence/2026-10-27/combined-read/deployment.json)。此次后台优化无需重新加载扩展；若尚未加载上一轮手动定位前端更新，仍需重新加载扩展。自动选择策略由模型依据通用工具定义和实际证据决定，无法保证每轮都减少相同次数或避免总时限。
