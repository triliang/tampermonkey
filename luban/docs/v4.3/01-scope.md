# Luban v4.3 需求范围草案

日期：2026-10-20  
状态：需求范围草案，尚未进行新版界面或真实运行验证。

## 版本定位与依据

v4.3 定位为“对话驱动的网页改造助手”：用户表达目标，Agent 自动收集证据、筛选和复核；用户只在范围确认、生成、运行、保存这些关键决策上参与。

本轮只明确需求范围，不修改功能代码。当前 `docs/v4.2` 是空目录，以下以现有源码、v4.1 评审和用户列出的作废原因为依据，不继承 v4.2 的流程设计。

## 一、版本目标

v4.3 聚焦三个结果：

1. **交互清楚**：对话、任务状态、脚本制品各有位置，用户无需理解内部工作流。
2. **筛选可信**：Agent 能主动补证据、排除误选、检查遗漏，并明确无法判断的范围。
3. **脚本完整**：用户看到、复制和导出的脚本都符合 Tampermonkey 格式。

本版优先改善现有隐藏、弱化能力，不扩展为任意网页编辑平台。

## 二、当前问题与优化方向

| 当前问题 | 对用户的影响 | v4.3 方向 |
|---|---|---|
| 需求、目标、方案、候选、检查卡片长期堆叠 | 分不清现在该看什么、做什么 | 对话保留交流，当前状态单独呈现，脚本进入制品视图 |
| 用户需要点击分析、确认、选方案、授权、继续等多个按钮 | 用户承担了 Agent 的编排工作 | 自动串联只读分析；只在必要决策处停下 |
| 分析按钮将系统指令写成用户发言 | 聊天被流程话术污染，意图来源混淆 | 操作事件与用户消息分开记录和展示 |
| 两套目标勾选、多个相近确认入口 | 选择结果和授权含义难理解 | 统一目标集合、统一确认入口 |
| 通用状态、长限制说明、操作按钮同等突出 | 窄侧栏信息密度过高 | 一个主要操作，细节按需展开 |
| 设置直接铺出连接、协议、模型参数 | 用户不清楚配置顺序和当前可用性 | 先展示可用状态，再按使用方式配置 |
| 候选只有正文，导出才补脚本头 | 复制出来不能直接安装，制品不一致 | 从候选阶段就提供完整用户脚本 |

## 三、功能性需求

### F1. 对话与制品的信息架构重整｜必做

界面分为四类信息，各自承担明确职责：

| 信息 | 默认呈现方式 |
|---|---|
| 用户诉求、澄清、结论 | 对话消息 |
| 正在分析、等待确认、中断等状态 | 输入区附近的紧凑状态区 |
| 目标范围、处理方式与关键确认 | 当前决策卡，同一时间只突出一项 |
| 脚本、版本、适用范围、运行记录 | 独立制品视图，对话内仅保留入口和摘要 |

具体规则：

- 需求摘要默认收起，修改需求或存在歧义时再展开。
- 历史确认保留为简短记录，不继续展示可操作的旧卡片。
- 工具活动合并成可折叠过程摘要，不展示内部推理。
- 分析结果回答“发现什么、建议什么、哪里不确定”，避免重复罗列全部结构节点。
- 脚本查看后返回对话，保留输入内容和阅读位置。
- 页面切换或目标失效时，明确指出受影响内容，阻止操作旧范围。

参考 pi-web 的消息类型区分、工具细节折叠、文件独立查看、统一颜色变量和键盘交互。针对侧栏空间重新设计，不直接搬入桌面多栏布局。具体源码观察、设计思路与适配规则见第八节。

### F2. Agent 自动推进与关键决策确认｜必做

用户表达需求并授权读取当前页面后，Agent 自动完成：

**理解需求 → 收集证据 → 检视候选 → 排除冲突 → 提交建议范围与方案。**

- 不再要求用户点击“下一步”“读取下一批”“继续已批准请求”来推动内部过程。
- 仅在缺少必要信息、证据不足或需要授权时打断。
- 范围与处理方式可以在一张决策卡内核对，减少重复展示。
- 目标确认、生成、运行、保存仍是独立授权，界面必须说明每个操作的实际含义。
- 已获授权后自动继续对应工作，不要求再次点击启动。
- 分析和普通聊天不得自动生成脚本。
- 用户修改需求、目标或代码后，重新校验受影响的确认，避免继续使用旧授权。

### F3. 提高元素筛选精准度｜必做

重点补齐证据与验证能力，而非只调整提示词。

| 能力 | 产品要求 |
|---|---|
| 按需查询 | 按页面区域、结构特征获取候选，减少 DOM 顺序和固定批次造成的遗漏 |
| 深入检视 | 查看祖先、兄弟、子树摘要、可见性、布局与包含关系 |
| 选择复核 | 检查嵌套重复、选择器不唯一、范围过大及保留内容混入 |
| 反例反馈 | 用户取消、排除或纠正的目标作为本任务约束，避免重复推荐 |
| 增量补证 | 补充证据时保留仍有效的选择；变化的目标单独失效 |
| 覆盖说明 | 区分已检查、未检查、不可访问和证据不足的区域 |
| 执行前校验 | 重新验证节点身份、唯一性和确认范围 |

不能把空文本、iframe、固定定位等结构特征直接判定成业务目标。站点专用规则不得进入产品默认逻辑。

### F4. 有界的分析与修复循环｜必做

“loop engineer”在本版定义为两种能力：

**运行时改进循环**

- 发现证据缺口后自动补充检视。
- 发现重复、误选或范围冲突后修订建议。
- 试运行后检查目标变化及非目标保留情况。
- 检查失败后可分析原因、提出修复候选；新代码仍需授权运行。
- 范围扩大必须重新确认，不能借修复自动扩大授权。

循环必须有次数、时间和调用预算，遇到无新证据、重复失败、页面失效或预算耗尽时停止，给出原因与可选行动。

**研发评估循环**

- 建立跨布局的任务集，包含正确目标、排除目标和保留约束。
- 记录失败原因，补充反例并回归验证。
- 对比改进前后的筛选、遗漏、误伤和成本。
- 评估案例不得转化为运行时站点特判。

Deep Agents 继续承担任务级编排；是否引入显式 LangGraph 子流程，由后续技术方案判断。需求验收依据行为和效果，不以“增加一个框架”为完成标准。

### F5. 设置体验重设计｜必做

建议将设置组织为：

- **模型与服务**：当前使用方式、模型、可用状态和切换入口。
- **设备与连接**：本地服务状态、配对状态和连接诊断。
- **外部入口**：已有集成的启用与状态。
- **高级选项**：端点、协议、超时等参数。

设计要求：

- 首屏先回答“现在是否可用、正在使用什么”。
- 按本地 Codex、API 服务等使用方式渐进展示相关字段。
- 使用服务卡片、状态标记、清晰分组和简短说明。
- 保存与测试分别反馈；失败能区分连接、凭据、模型及能力问题。
- 不靠更换名称掩盖原有表单复杂度。
- 保留已有配置，避免升级后要求用户重新填写。

### F6. 统一 Tampermonkey 脚本制品｜必做

从候选阶段开始，展示完整用户脚本，包含：

- `==UserScript==` 元数据边界；
- 名称、命名空间、版本、说明；
- 已确认的 `@match`；
- 合适的 `@run-at`；
- 实际需要的 `@grant`，无特权 API 时使用 `none`。

具体规则：

- 元数据由产品根据结构化信息组装和校验，模型负责功能正文。
- 候选、编辑、复制、保存和导出使用统一制品规则。
- 同一版本的复制内容与导出内容保持一致。
- 不产生重复脚本头。
- 修改适用范围、权限或运行时机后，触发对应复核。
- 权限仍由结构化授权控制，不能通过编辑注释提权。
- 旧脚本补齐元数据时保留原正文；不能确认范围或权限的脚本标记待复核。
- 扩展内可运行与 Tampermonkey 可安装、可运行分别验收。

## 四、非功能性需求

| 类别 | 要求与验收方向 |
|---|---|
| 易用性 | 用户无需操作内部分析步骤；当前状态和下一项必要决策始终清楚 |
| 视觉一致性 | 统一字体、间距、颜色、按钮层级及加载、错误、空状态 |
| 可访问性 | 核心操作支持键盘；状态不只靠颜色表达；焦点可见 |
| 筛选质量 | 分别评估精准率、召回率、范围正确性与保留区域误伤，不能只看选择器是否命中 |
| 可靠性 | 重连、重试、恢复不重复生成、运行或保存；旧任务回执不能覆盖新任务 |
| 状态一致性 | 聊天摘要、确认范围、制品版本和运行结果对应同一任务修订 |
| 性能与成本 | 按需采集、限制证据体积、设置循环预算；可停止，避免无收益重复调用 |
| 隐私与安全 | 页面内容视为数据；最小化采集与外发；凭据和敏感信息不得进入展示及诊断日志 |
| 可观测性 | 能追溯使用了什么证据、为何停止、修改了哪些目标以及对应制品版本 |
| 兼容与迁移 | 保留现有脚本、会话和配置；明确 iframe、Shadow DOM、视觉模型等能力边界 |
| 通用性 | 使用跨站、跨布局及反例验收，不引入网站专属默认规则 |

质量提升幅度、延迟和调用成本门槛，在冻结范围后依据当前链路基线确定。本阶段不编造达标数字。

## 五、增强项与不纳入范围

**增强项：核心能力完成后评估**

- 少量候选区域截图，辅助支持视觉的模型判断。
- 独立只读复核代理，审查误选和证据缺口。
- 更深入的 iframe、Shadow DOM 支持，需明确权限和覆盖边界。

**本版不纳入**

- 全自动无限重试、自动运行或自动保存。
- 任意网页操作、表单提交、交易等能力扩张。
- 通用文件系统、Shell 或任意外部工具开放。
- 网站专属选择器库和任务识别特判。
- 新增外部集成渠道。
- 大规模长期记忆或模型训练平台。

## 六、版本验收场景

1. 用户提出明确需求后，Agent 自动完成只读分析，过程中无需逐步点击。
2. 用户能区分结论、等待确认事项和脚本制品，历史卡片不堆叠。
3. 用户排除某区域后，后续分析尊重该约束。
4. 嵌套、动态替换及同类重复元素场景下，能发现范围冲突或目标失效。
5. 试运行检查同时覆盖预期变化与非目标保留，无法判断时明确说明。
6. 中断恢复不重复执行；修订代码不会沿用旧版本运行授权。
7. 新候选直接提供完整用户脚本，复制与导出一致，并通过真实 Tampermonkey 安装运行验证。
8. 设置首屏能看出当前是否可用，完成配置不依赖理解底层协议。
9. 每轮工具过程可折叠查看，结论和待授权事项不被折叠隐藏；不会把按钮事件显示为用户发言。
10. 打开脚本再返回聊天时，保留未发送文字和阅读位置；阅读历史时不因新消息被强制拉回底部。
11. 核心路径可用键盘完成，关闭制品或设置后焦点回到合理位置；停止与错误均有可读文字说明。

### 8.2 九个可借鉴的设计模式

#### 1. 消息按职责区分，工具结果归入对应操作

**源码事实**：`MessageView` 按 user、assistant、custom、bashExecution 等类型分派渲染；已配对的工具结果归入工具调用，不再单独重复渲染。依据：[MessageView.tsx:255](/Users/jinxiong.yang/Code/pi-web/components/MessageView.tsx:255)。

**设计思路（推断）**：让一次操作的说明和结果具有完整上下文，避免同一信息在消息流中出现多份。

**Luban 适配**：

- 区分用户发言、Agent 结论、工具活动、授权事件和制品引用。
- “重新分析”“确认范围”等操作显示为简短事件，不伪装成用户自然语言消息。
- 页面检视与其结果放在同一过程记录中，对话正文只呈现与需求相关的结论。
- 用户诉求以原始发言为依据；需求摘要是可修订的辅助信息，不反过来覆盖原意。

不继承与网页改造无关的命令消息和会话树能力。对应 F1、F2。

#### 2. 每轮过程与最终回答分层

**源码事实**：`ChatWindow` 定义可折叠过程组，显示消息数、工具数和展开状态；无最终回答时默认展开，有最终回答后新挂载的过程组默认折叠，搜索命中可展开。已经展开的组是否随完成自动收起，不能据此认定。依据：[ChatWindow.tsx:195](/Users/jinxiong.yang/Code/pi-web/components/ChatWindow.tsx:195)、[ChatWindow.tsx:1152](/Users/jinxiong.yang/Code/pi-web/components/ChatWindow.tsx:1152)。

**设计思路（推断）**：运行时允许追踪工作，完成后把阅读重点交还给结果。

**Luban 适配**：

- 每轮只保留一个可展开的“分析过程”入口，包含检视、补证和复核摘要。
- 完成后优先展示“发现了什么、建议处理什么、还缺什么证据”。
- 工具证据可回看；内部推理不进入用户界面。
- 需要确认的事项、失败原因及补救操作保持可见，不藏进过程折叠区。
- 用户手动展开过程后，不因状态刷新反复折叠。

过程摘要不能替代关键决策卡，也不能变成要求用户逐项完成的步骤清单。对应 F1、F2、F4。

#### 3. 文件有独立阅读空间，对话保留入口

**源码事实**：`AppShell` 按文件路径创建或激活独立文件页签，打开右侧面板；移动端关闭抽屉并显示文件面板。`TabBar` 支持横向滚动页签。依据：[AppShell.tsx:1036](/Users/jinxiong.yang/Code/pi-web/components/AppShell.tsx:1036)、[TabBar.tsx:30](/Users/jinxiong.yang/Code/pi-web/components/TabBar.tsx:30)。

**设计思路（推断）**：对话负责协作，文件内容有稳定空间供阅读和操作。

**Luban 适配**：

- 对话只展示脚本名称、版本、变更摘要和“查看脚本”入口，不直接铺出长代码。
- 窄侧栏以独立制品视图替换聊天主区域，提供明确的“返回对话”。
- 制品内展示完整用户脚本、适用范围、权限、版本状态和对应运行记录。
- 复制、运行、保存针对当前显示版本；切换版本不能误用上一版的授权或回执。
- 运行后在制品中保留详细结果，对话只给简短结果和必要决策。

不直接搬入双栏、多文件页签和终端；独立制品视图是信息职责分离，不要求扩大侧栏。对应 F1、F6。

#### 4. 执行中仍能表达意图，并明确何时生效

**源码事实**：`ChatInput` 区分 steer 与 followup，显示排队消息；在没有打开菜单且不处于输入法组合输入时，Esc 可停止 Agent。依据：[ChatInput.tsx:1118](/Users/jinxiong.yang/Code/pi-web/components/ChatInput.tsx:1118)、[ChatInput.tsx:1560](/Users/jinxiong.yang/Code/pi-web/components/ChatInput.tsx:1560)、[ChatInput.tsx:1301](/Users/jinxiong.yang/Code/pi-web/components/ChatInput.tsx:1301)。

**设计思路（推断）**：忙碌状态不应完全阻断用户表达，但系统必须说明新消息何时作用于任务。

**Luban 适配**：

- 分析期间允许编辑输入，停止入口保持可见。
- 若允许发送补充要求，必须说明是影响本次分析，还是在本次结束后处理，不能悄悄吞入运行中的任务。
- 修改目标或保留约束后，先重新校验相关确认；消息发送不等于授权执行。
- v4.3 不要求复制完整的双队列机制；若暂不支持执行中提交，明确提示并保留输入草稿。

不向用户暴露 steer/followup 术语，不把队列提交直接视为代码运行或保存授权。对应 F2、F4。

#### 5. 阅读位置属于用户状态

**源码事实**：`ChatWindow` 分批载入历史消息并保持滚动位置；离开时保存底部状态，或保存消息锚点与偏移，恢复时查找对应锚点。依据：[ChatWindow.tsx:463](/Users/jinxiong.yang/Code/pi-web/components/ChatWindow.tsx:463)、[ChatWindow.tsx:487](/Users/jinxiong.yang/Code/pi-web/components/ChatWindow.tsx:487)。这些代码本身不足以证明所有流式更新场景都不会抢滚动。

**设计思路（推断）**：打开文件、切换会话、载入历史都不应破坏用户正在阅读的位置。

**Luban 适配**：

- 打开制品或设置再返回，恢复原聊天阅读位置。
- 用户阅读历史时，新结果显示“查看最新”入口，不强制跳到底部。
- 用户主动跟随最新消息时，保持合理的更新跟随。
- 目标证据展开和收起时，避免明显的阅读跳动。

不引入与本版无关的长会话分支系统。对应 F1 及易用性、可靠性要求。

#### 6. 输入草稿和制品阅读状态分别保存

**源码事实**：`ChatInput` 按 draftKey 保存与恢复文字、附件；`FileViewer` 恢复显示模式、折行和滚动位置；`AppShell` 按页签和 viewerRevision 接收阅读状态。依据：[ChatInput.tsx:515](/Users/jinxiong.yang/Code/pi-web/components/ChatInput.tsx:515)、[ChatInput.tsx:810](/Users/jinxiong.yang/Code/pi-web/components/ChatInput.tsx:810)、[FileViewer.tsx:1145](/Users/jinxiong.yang/Code/pi-web/components/FileViewer.tsx:1145)、[AppShell.tsx:536](/Users/jinxiong.yang/Code/pi-web/components/AppShell.tsx:536)。

**设计思路（推断）**：“回来继续”既包括聊天，也包括尚未发送的内容和正在阅读的制品。

**Luban 适配**：输入草稿按任务和绑定页面隔离；制品阅读状态按制品与版本恢复；恢复界面状态不恢复旧页面授权。迟到的旧版本结果不得覆盖新版本状态。不把所有任务草稿放在同一个全局恢复位置。对应 F1、F6 及状态一致性要求。

#### 7. 设置先选服务，再进入详情

**源码事实**：`ModelsConfig` 可搜索未配置服务，以名称、副标题和边框卡片呈现入口；主配置包含已启用服务、自定义服务、模型树与详情；模型发现有加载、错误、搜索及已添加状态。依据：[ModelsConfig.tsx:1708](/Users/jinxiong.yang/Code/pi-web/components/ModelsConfig.tsx:1708)、[ModelsConfig.tsx:1714](/Users/jinxiong.yang/Code/pi-web/components/ModelsConfig.tsx:1714)、[ModelsConfig.tsx:2027](/Users/jinxiong.yang/Code/pi-web/components/ModelsConfig.tsx:2027)、[ModelsConfig.tsx:432](/Users/jinxiong.yang/Code/pi-web/components/ModelsConfig.tsx:432)。

**设计思路（推断）**：先让用户选择想连接的对象，再显示完成配置所需的信息，减少一次性表单负担。

**Luban 适配**：

- 设置首页使用摘要卡呈现当前模型服务和本地连接，显示状态文字及主要操作。
- “添加或切换服务”先展示已有支持的使用方式；服务较多时提供搜索。
- 进入具体服务后，再呈现凭据、模型、测试及高级选项；只显示该方式相关字段。
- 未配置、连接中、可用和失败分别呈现，错误旁提供对应处理入口。
- 窄侧栏采用“列表 → 详情 → 返回”，不复制宽弹窗内的双栏服务树。

pi-web 仍展示 OAuth/API Key、协议及配置路径；不能据此声称其已经消除技术术语。Luban 应保留必要概念的准确性，减少首页暴露的参数数量。对应 F5。

#### 8. 用语义颜色统一层级，控制长内容占用

**源码事实**：`globals.css` 集中定义背景、面板、悬停、选中、边框、正文、弱文字、强调色及消息/工具背景，并提供暗色对应值；`MessageView` 对长用户气泡设置高度上限。依据：[globals.css:23](/Users/jinxiong.yang/Code/pi-web/app/globals.css:23)、[globals.css:45](/Users/jinxiong.yang/Code/pi-web/app/globals.css:45)、[MessageView.tsx:150](/Users/jinxiong.yang/Code/pi-web/components/MessageView.tsx:150)。

**设计思路（推断）**：用一致的视觉角色表达层级，以少量强调色引导主要操作，避免每个模块各自争夺注意力。

**Luban 适配**：

- 统一背景、容器、边框、正文、辅助文字、强调色和状态色的语义变量。
- 主操作使用强调色，过程详情与次要说明保持较弱视觉权重。
- 需求、目标、方案不再全部使用同等强度的独立卡片。
- 统一字体、间距、圆角和交互尺寸；长证据按需展开，代码在制品视图阅读。

不直接复制桌面内容宽度、固定气泡高度或过小字号；避免在窄侧栏中形成多层嵌套滚动。多主题扩展不因此成为本版必做功能。对应 F1、F5 及视觉一致性要求。

#### 9. 键盘与辅助语义落实到具体控件

**源码事实**：`TabBar` 使用 tablist/tab、aria-selected 和焦点索引，支持方向键、Home/End、Enter/空格；文件控件有 focus-visible 样式。依据：[TabBar.tsx:31](/Users/jinxiong.yang/Code/pi-web/components/TabBar.tsx:31)、[globals.css:1345](/Users/jinxiong.yang/Code/pi-web/app/globals.css:1345)。

**设计思路（推断）**：当前选中项、展开状态和可执行动作应可被键盘用户和辅助技术识别。

**Luban 适配**：过程折叠区暴露展开状态；图标按钮有可读名称；范围确认、停止和错误不只依靠颜色；打开/关闭制品或设置时合理移动并恢复焦点。快捷键不得干扰中文输入法组合输入。

不能仅通过添加 aria 属性认定达标，需真实验证焦点顺序、弹层返回焦点及状态播报。对应可访问性要求。

### 8.3 建议的侧栏信息布局

以下是 Luban 的适配建议，不是 pi-web 现有界面的复刻或最终视觉稿：

```text
顶栏：当前页面/任务摘要 · 工具库 · 设置

对话区
  用户：原始诉求与补充
  Agent：结论、依据摘要与不确定性
  分析过程：可折叠的工具活动与证据
  脚本入口：名称、版本、变更摘要、查看脚本

当前决策区（仅在需要用户决定时出现）
  例如：核对处理范围与方案
  一个主要操作 + 修改/取消等次要操作

输入区附近的状态：正在分析 / 等待确认 / 已停止
输入区：补充要求 · 发送或停止

独立制品视图（打开时替换聊天主区域）
  返回对话 · 脚本名称与版本
  适用范围、权限和状态摘要
  完整脚本与本版本运行记录
  与当前版本及授权状态相符的操作
```

当前决策区只负责关键决策，不展示完整步骤条；正常分析阶段不要求用户驱动工具调用。制品中的运行、保存动作仍遵守 F2、F6 的独立授权要求。

### 8.4 落地优先级与检查方式

| 优先级 | 参考模式 | Luban 应达到的结果 | 检查方式 |
|---|---|---|---|
| 第一优先 | 消息分类、过程与结论分层、独立制品 | 诉求、结果、过程、脚本不再堆成同等卡片 | 走完分析到保存路径，检查每项信息只有清晰职责和对应入口 |
| 第一优先 | 服务选择与详情分离 | 首屏看得懂是否可用，详细参数按需出现 | 分别检查首次配置、已有配置、连接失败与切换服务 |
| 第二优先 | 阅读位置、草稿与版本状态恢复 | 打开制品返回后可继续阅读和输入，不串任务或版本 | 切换视图、重开侧栏、切换页面并模拟迟到回执 |
| 贯穿实施 | 视觉变量、键盘及状态语义 | 主操作突出，窄侧栏可读，核心路径可用键盘完成 | 在实际支持的侧栏宽度、主题和键盘操作下验收 |

上述优先级表示 v4.3 核心需求的实施顺序，不降低既有非功能性要求，也不新增双队列、多主题、终端或多栏工作台等范围。当前仅完成源码参考分析，尚未完成这些交互的实现与验收。
