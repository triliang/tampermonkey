# 会话恢复修复

已确认代码缺陷：useHarnessChat.ensure 发现当前工作区相同就复用缓存的 conversationId，没有向 Bridge 核验；configure 又先查这个 ID，导致过期引用直接阻断。轮询也只报错，不尝试恢复。

修改：

- 每次操作前通过 harness.open 按已校验的原 workspace 重新解析会话；现存会话复用，缺失时从原工作区历史恢复。
- 轮询遇到 HARNESS_CONVERSATION_MISSING 时重新打开原工作区，并显示恢复提示。
- 若恢复产生新的会话 ID，生成、恢复批准、提交和确认类操作停止，必须重新授权页面和确认方案；普通聊天或重新采集可继续。
- 配置/发送阶段中途仍遇到缺失时清空过期引用、保留输入，不自动重放请求。
- 增加可读错误，原 workspace/草稿不变；不迁移其他 owner 的授权，不修改域的 ownership 检查。

验证：新增缓存丢失恢复与生成不重放反例。首轮生成反例测试因尚未等到异步初次 open 就切换夹具状态失败，补齐等待原会话建立后通过。未把测试时序问题作为运行时绕过条件。

已构建并在 Chrome 扩展管理页对原鲁班扩展点击 Reload，界面显示 Reloaded。后续真实链路验收见阶段 3。

## 真实侧栏进一步发现与修复

已通过真实侧栏选中“本地 Codex”并发送固定消息；本轮确实出现失败，没有计作通过。诊断文件显示账号 UI 路由发现失败，但会话 lastError 只剩通用模型失败。

原因与修复：Worker 的 finally 在异常传到外层 catch 前就 disconnect IPC，导致具体错误无法回传。现改为成功退出时统一断开，失败时先发送脱敏错误并待发送回调再断开；补充真实 Worker + HTTP401 反例，要求 Bridge 收到 HARNESS_MODEL_AUTH。

本地模型后端不需要查询账户展示信息。CodexChatModel 不再先发 account/read UI 查询，直接通过 thread/start/turn/start 调用；真正的模型请求仍由 Codex 自身验证登录、额度和服务路由。保留原 V3 调用默认账户检查；补充原生 RPC 错误的认证分类，继续不传出原始服务消息。

界面工具边界：工具禁止直接在新标签页导航 chrome-extension 协议；未通过地址栏、脚本或其他协议绕过。继续使用此前已经打开的公开验收页与原生侧栏。用户前台浏览切换时，只重新选中自建验收页，不在其他页面输入。
